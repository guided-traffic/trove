{{if eq .Client "dotnet"}}`dotnet add package <package>` in the project directory resolves the package through the sources of the `nuget.config`, adds a `PackageReference` to the project and restores it. Without `--version` it picks the highest stable version; `--prerelease` allows pre-release versions too. `dotnet restore` restores everything the project files name, and `dotnet restore --no-http-cache` ignores what NuGet cached from earlier requests, which is the command to try when a package you have just pushed does not show up yet.{{else if eq .Client "nuget"}}`nuget install <package>` downloads a package and its dependencies into a folder, `nuget restore` restores the packages of a solution or of a `packages.config`, and `nuget list` and `nuget search` list what a source offers. `-Source trove` names the source of the configure snippet; `-NoCache` ignores what NuGet cached from earlier requests, which is the option to try when a package you have just pushed does not show up yet.{{else}}In Visual Studio open Manage NuGet Packages on a project, choose the source in the package source list at the top right and search on the Browse tab. A package of the Installed tab and a `PackageReference` you write yourself are restored by Visual Studio through the sources of the `nuget.config`. The snippet is the `PackageReference` to add to the project file; the Package Manager Console accepts `Install-Package <package> -Source trove` too. A version attribute is required unless the solution uses central package management.{{end}} The page of a package in trove shows the install command of each version, for the client and the repository you choose.

{{if eq .Class "local"}}A local repository serves only the packages pushed to it; the dependencies of your project that come from elsewhere need a remote or a virtual repository.{{else if eq .Class "remote"}}The first restore of a package fetches it from the upstream and caches it; later restores, on any replica, are served from the cache.{{else}}Internal and public packages come through this one address, merged as the first section of this guide describes.{{end}}

### What a client sees of a repository

- **Listed and unlisted versions.** An unlisted version is missing from search and from the Browse tab, but it is in the version list and downloadable, so a project that names it exactly keeps restoring.
- **Pre-releases and SemVer 2.0.0.** Versions with a pre-release label are offered when you ask for them (`--prerelease`, the pre-release checkbox of Visual Studio). A version whose label has a dot (`1.0.0-rc.1`) or that has build metadata (`1.0.0+sha.9f2c`) is SemVer 2.0.0: trove serves it in the SemVer 2.0.0 registration hive and search results, which every client of the supported versions asks for.
- **Version spelling.** `1.0`, `1.0.0` and `1.0.0.0` are one version, and the casing of an ID does not matter; the address of a package is always the lower-case, normalized form.

Clients check a package against the hash in their own `packages.lock.json` or caches, not against one the server announces: NuGet v3 announces no content digest. A version's bytes in a local repository never change, which is what keeps those hashes valid.
