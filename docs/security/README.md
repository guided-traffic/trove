# Security architecture

Status: the mechanisms that are built are described here, each on the page of its perspective: from M0 the listeners and their
TLS, the client-address and endpoint rules, the stored-secret key ring, the egress address policy, the PostgreSQL and Valkey
connections and grants, the coordination of replicas, and the chart's security context and network ingress; from M1 the identity,
the permissions, the audit trail, the file transfer and the endpoints and their exposure; from M2 the repositories, the generic
engine of the remote repositories, the upstream credentials and the npm format; from M3 the NuGet format (publish, remote and
virtual classes); from phase 5a the projects and their delegated administration; from M4 the CI federation (issuers, signing keys,
mappings, the token exchange); from M13 (phase 5b) the trove Bastion; from M4b (phase 6) the vulnerability scanning; from phase 6a
the cut of the replicas into the roles `api`, `packages` and `worker`; from phase 6b the mirror mode of remote repositories; the
shared asset store of the UI's rolling upgrades (R-HA-020); the user avatar upload (R-API-055); and from phase 7 the backup and
restore lane, whose page covers the backup credentials, the run record and the hold, the revocation journal and what a restore
trusts; from phase T-16 the token service and the registry tokens of the OCI registry.

This directory describes trove's security architecture, with one page per perspective. It is deliberately not one document that
covers everything, because nobody finishes such a document and so nobody checks it. The file names are the index.

How to report a vulnerability is in [SECURITY.md](../../SECURITY.md). This directory covers what is already known.

## Form

- **One perspective per page.** Each page explains one view of the system: who is trusted with what, where credentials go, what
  the deployment is allowed to do. It references the code that implements the view and says only what the code does.
- **Every page ends with `## What this does not cover`.** That section lists the open gaps of the page's mechanisms.
- **Open gaps carry a stable identifier.** A gap is a `### H-<n> · <title>` heading in the `What this does not cover` section of
  the one page that records it: the security page of its mechanism for a gap this directory owns, the spec page for a gap the
  specification owns. It is never collected in a central list. The number stays the same for the gap's whole life, so reviews,
  commits and issues can refer to it.
- **A spec-owned gap is linked under its number.** The security page of the mechanism links every gap of the spec pages that its
  mechanisms have, as a bullet `- [H-<n>](../spec/<page>.md#<anchor>)` with one line, at the top of its `What this does not cover`
  section, before its own headings. A mention in the body does not replace the link.
- **Each gap states its case.** It names the component and the subject it affects, says whether it is live today or dormant (and
  what would make it live), and says what makes it real.
- **No tickets, no checkbox lists, and no promises of future work** on these pages. They describe the system as it is.
- Security notes appear only where a real security relation exists.
